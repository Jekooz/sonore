2. DEFECTS FOUND AND FIXED
====================================================================
D1. `flutter analyze`: 13 errors — `Override` is not a type.
    Riverpod 3.4.3 (pubspec.lock) no longer exports `Override` from
    `package:riverpod/riverpod.dart`; it is exported only through
    `package:riverpod/misc.dart`. Proved before fixing, with a minimal
    probe: importing from `riverpod.dart` or `flutter_riverpod.dart`
    fails, importing `riverpod/misc.dart show Override` compiles.
    test/support/harness.dart
    test/lyrics_screen_test.dart

D2. `flutter analyze`: undefined name `Skeleton` — the lyrics widget
    test never imported the widget's library.
    test/lyrics_screen_test.dart           (+ lib/ui/screen_states.dart)

D3. `tool/check_tokens.sh`: 1 violation —
    `BorderRadius.circular(Tokens.rSmall)` at
    lib/features/lyrics/lyrics_screen.dart:335. Radii belong to the
    theme, so the value moved there as `Tokens.rSmallBorder` (the same
    rSmall radius, for widgets that take a BorderRadius rather than an
    OutlinedBorder) and the screen uses the token.
    lib/theme/tokens.dart
    lib/features/lyrics/lyrics_screen.dart

D4. Lyrics data layer failed 4/4 with `YtmOfflineException` from
    api_client.dart:154. The test's MockClient answered every path —
    including the discovery probe `GET /health` — with the lyrics body,
    so `_isHealthy` (which requires a body containing `"ok"`) never
    matched and discovery concluded the sidecar was down. The mock now
    routes `/health` to the same payload shape as
    test/fixtures/health.json.
    test/lyrics_screen_test.dart

D5. Context menu: 5 tests plus the context-menu golden could not find
    "Play now". Batch 3 added a Settings action to the shell's nav rail
    (desktop) and bottom bar (phone) drawn with `AppIcons.dotsThree`.
    It precedes the content in tree order, so
    `find.byIcon(AppIcons.dotsThree).first` tapped Settings, not the
    row's overflow. The tests now scope the tap to the first row's own
    overflow button; the product code was not changed.
    test/product_screens_test.dart           (firstRowOverflow helper, 5 sites)
    test/golden/product_screens_golden_test.dart

D6. "No lyrics for this track." was unreachable, and the loading
    skeleton test observed data instead of loading.
    (a) lib/ui/data_states.dart decided `current == null -> error`
        before consulting `isEmpty`. For `DataStateView<LyricsResult?>`
        a null value IS a legitimate answer ("the service has no
        lyrics"), so the empty state was dead code and the screen showed
        "Something went wrong loading this." instead. The check is now
        `value.hasValue` — "the provider never produced a value" is a
        different thing from "the provider answered null".
    (b) The skeleton test used a 30-second `Future.delayed` while
        `pumpAndSettle` pumps through the skeleton's own shimmer
        animation, so the widget-test clock ran past the delay and the
        data arrived. A never-completing Completer plus `settle: false`
        keeps the screen in loading deterministically.
    lib/ui/data_states.dart
    test/lyrics_screen_test.dart

No production file outside these was touched. The setters, the store,
the equalizer, the settings screen and the lyrics screen were read and
left as they are: no defect in them was demonstrated.

3. WHAT BATCH 3 DELIVERS (verified by the suite below)
====================================================================
Settings screen (lib/features/settings/settings_screen.dart), grouped
sections as design.md section I asks, every control wired to the real
store:
  Appearance   reduce transparency, reduce motion, text scale, theme note
  Lyrics       follow playback
  Audio        equalizer summary + link to the EQ screen
  Diagnostics  live connection + local-runtime state, re-check action
  Account      sign-in state, sign out (behind a confirmation)
  Privacy      where the session lives, stated plainly
  About        version, licences
  Footer       Reset preferences, behind a confirmation

Persistence (lib/core/app_settings.dart, settings_persistence.dart):
`shared_preferences` store, read before the first frame in main.dart so
the app opens on the stored preferences, per-write save status surfaced
as a banner, and a reset that returns every field to its default.
Equalizer shape is persisted on every change and re-applied to the
engine at startup (playback_service._applyPersistedEqualizer).

Lyrics (features/lyrics/): timed lyrics follow playback and each timed
line is a seek target; untimed lyrics render as static text and are not
offered as seek targets; empty, offline, signed-out and failed states
each say their own thing.

6. DIFFERENCES FROM design.md SECTION I (deliberate, not stubs)
====================================================================
The Settings screen states each of these in the UI itself:
- No autoplay switch, no output-device picker, no theme switch: the
  audio engine exposes none of them and v1 ships dark-only, so a control
  for any of them would be decorative (project non-negotiable: no mock
  or inert in-scope controls).
- No Cache & storage section and no Keyboard-shortcuts page: neither
  behaviour exists yet in the Flutter app ($5 phases own them), so
  sections for them would be empty promises.
These are recorded here as differences, not as unfinished work.
